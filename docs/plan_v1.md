## 1. 技术架构

```
Astro（静态输出）
├─ 内容层   Content Collections + Zod    ← 只固定公共结构，不固定视觉类型
├─ 渲染层   renderer registry            ← 场景视觉可无限扩展
├─ 地图层   d3-geo + TopoJSON，运行时投影为 SVG，镜头由叙事驱动
└─ 样式层   两层 CSS 令牌：全站基础 + 作品/场景主题
```

不引入：MapLibre / Leaflet（会把作品变回 GIS 工具）、React（island 用原生 TS 足够）、
CMS 与后端（首版无服务端需求）、动画库（滚动联动手写可控，证明不够用再引入）。

## 2. 内容数据模型

成功标准 6（能复用到其他文明）押在这份设计上。核心策略：**把稳定的固定死，把不稳定的留开放**。

### 2.1 稳定的公共结构（全站唯一契约）

只有以下八项是全站永久稳定的：

| 公共结构 | 说明 |
|---|---|
| 时间 | 标签、排序键、精度（日/月/年/区间）、纪年体系 |
| 历史对象 | 人物、地点、政权、事件、制度、文物、史料——独立实体，场景只引用 id |
| 论断 | 每条论断带证据状态与来源关系 |
| 来源 | 独立实体，见 §2.4 |
| 图像与授权 | 独立实体，见 §2.5 |
| 地理信息及精度 | 每个图层标注适用年代与精度等级 |
| 不确定性 | 论断、地理、数字、图像各自的不确定性表达 |
| 注释与分层阅读 | 主线之外的可展开层 |

**公共 schema 不枚举场景类型**，也不假定所有历史场景最终能归入某几类。

### 2.2 视觉层：renderer registry

```ts
// 公共 schema 里，一个 beat 的视觉只长这样：
visual: {
  renderer: string,                    // 已注册的 renderer id
  config: Record<string, unknown>      // 由该 renderer 自带的 schema 二次校验
}
```

校验分两步：公共 schema 只确认 `renderer` 是已注册 id；随后用该 renderer 声明的 Zod schema 校验 `config`。
新增一种历史表达 = 注册一个 renderer + 一份 config schema，**不触碰公共结构，不改动已有内容**。

首轮实现三个渲染器，它们是首轮实验的需要，不是全站的封闭清单：

| renderer id | 用于 | 首轮对应 |
|---|---|---|
| `map-narrative` | 疆域、行军、路线 | 卢比孔河 |
| `actor-array` | 人物集合、权力构成、群体变化 | 三月十五日 |
| `structure-compare` | 制度、机构、前后对照 | 奥古斯都掌权 |

已预见但**尚未实现**的类型（registry 必须能容纳，schema 不得妨碍）：贸易网络、宗教传播、
迁徙、城市演变、考古地层、文本流变、书信与文献网络、气候与农业、疫病、货币与物价。

### 2.3 层级与出版状态

```
work（作品/卷）→ chapter（章节）→ scene（场景）→ beat（拍）
```

层级保留，但每一级都带出版状态，**数据与界面都必须显示**：

```ts
status: 'sample'    // 实验样章——为验证方法而做，不代表完整叙述
      | 'draft'     // 草稿——内容未完成或未核实
      | 'chapter'   // 完整章节
      | 'published' // 已发布作品
```

当前三个场景一律为 `sample`，且**可能来自不同章节**。界面上必须让读者清楚：
这是《共和国危机（前133—前27）》的实验样章，不是对这段历史的完整讲述。
不得出现"三个场景共同构成一部完整作品"的暗示。

### 2.4 论断与来源

来源是独立实体，不再是一行字符串。

```ts
// src/content/sources/<id>.yaml
{
  id: string,
  kind: 'ancient' | 'modern' | 'epigraphic' | 'numismatic' | 'archaeological' | 'documentary',
  author:   { name, nameZh?, floruit? },
  title:    { original?, zh, en? },
  locusScheme?: string,            // 该作品的标准定位格式，如 "卷.章"
  composed?: { label, sortKey?, note? },        // 成书 / 成文年代
  language?: 'la' | 'grc' | 'zh' | 'en',        // 原文语言
  edition?:  { text?, translator?, publisher?, year?, isbn? },
  url?: string,
  accessed?: string,               // ISO 日期
  stance?: I18n,                   // 立场：如"当事人自述，有夸大对手规模的动机"
  limits?: I18n                    // 使用限制：如"仅存节本""经后世转录"
}

// 论断
{
  text: I18n,
  status: 'attested' | 'inferred' | 'disputed' | 'legend',
  citations: [{
    source: string,                                     // 来源实体 id
    locus?: string,                                     // 篇章 / 页码定位
    relation: 'supports' | 'contradicts' | 'contextualises' | 'later-tradition',
    note?: I18n
  }],
  alternatives?: [{ text: I18n, citations: [...] }],    // 替代解释，disputed 时必填
  uncertainty?: I18n
}
```

约束（由 schema + 组件共同保证）：

- `status` 为 `inferred` / `disputed` / `legend` 的论断，界面上必须与确证史实有可见区别；
- `status: 'disputed'` 必须提供 `alternatives`；
- 每条关键论断必须能在界面上展开其 `citations`；
- 开发期允许 `citations` 暂缺并标记为 `draft`，但 `status: 'chapter'` 及以上的内容构建时校验为必填。

> `ref: "Caes. BC 1.8"` 这种写法只在 M0 分镜阶段作为占位符使用，M3 前必须全部迁移到来源实体。

### 2.5 图像与授权

```ts
{
  file: string,
  kind: 'artefact' | 'site' | 'map' | 'manuscript' | 'reconstruction' | 'ai-assisted',
  alt: I18n,                       // 必填
  caption: I18n,
  creator?: string,                // 创作者 / 摄影者
  holder?: string,                 // 收藏或提供机构
  license: { name: string, url: string },
  sourceUrl: string,               // 原始页面
  accessed: string,
  processing?: ('cropped' | 'colour-adjusted' | 'background-removed' | 'upscaled' | 'composited')[]
}
```

`kind` 为 `reconstruction` 或 `ai-assisted` 时，界面**强制**显示"非原始史料"标记，不可关闭。
`license` / `sourceUrl` / `accessed` / `alt` 缺失则构建失败。

### 2.6 地理信息及精度

```ts
{
  data: string,                    // TopoJSON 路径
  validFor: string,                // 适用年代
  accuracy: 'survey'      // 现代测绘数据
          | 'scholarly'   // 学界重建，有争议但有依据
          | 'schematic'   // 示意，不代表真实边界
          | 'disputed',   // 位置或范围本身存在争议
  note?: I18n
}
```

`schematic` 与 `disputed` 的图层在地图上必须有可见的绘制区别（如虚线、羽化边缘），
并在图例中说明。不得让示意内容与确证地理事实长得一样。

## 4. 场景一设计：《卢比孔河》

**这一屏要让读者理解什么**：不是"凯撒渡了一条河"，而是——罗马共和国对军事力量的约束是**空间性**的，
跨过行省边界这个动作同时改变了法定权限、政治定性、当事人自身的辩护立场和实际后果；
而这几件事的变化方向并不一致，其中一部分至今仍有争议。

### 4.1 六拍（M0 阶段细化，措辞待史料核实后定稿）

| 拍 | 视觉 | 论点方向（**非定稿**） |
|---|---|---|
| 1 | 军团地图 + 制度授权带（默认）；人际关系为按需层，三类关系**不同时显示** | 权力正在向少数拥有军队和政治网络的个人集中 |
| 2 | imperium 四维面板（见 §4.3） | 共和国对军事力量的约束是空间性的——这是理解全场景的钥匙 |
| 3 | 前 49 年 1 月上旬的政治过程，镜头落到拉文纳 | 元老院的常规政治协调已经失效，冲突进入非常措施阶段 |
| 4 | **媒介转换**（见 §4.2） | 这个决定性的位置，我们其实并不确切知道在哪 |
| 5 | 越河：四个维度各自变化，方向不一致 | 什么都没发生，又什么都变了——但"变了什么"取决于谁在解释 |
| 6 | 意大利境内可用军力与城市态度的分布 | 凯撒行动成功不仅来自决断，也与意大利境内未能迅速形成有效抵抗有关 |

第 1、3、6 拍的论点是从原方案的绝对化表述改写来的（原文见 `decisions.md` 修订表）。
改写原则：把绝对判断改为范围明确、可被证据支持的判断；每条关键论断可展开来源；
有争议处并列替代解释；不把复杂政治过程写成注定发生的结局。

### 4.2 第 4 拍：媒介转换，不是连续放大

原方案"从数百公里连续放大到十几米"会制造虚假精确——底图数据支撑不到那个尺度，
而卢比孔河的古代河道与渡河位置本身就有争议。改为四段**明确切换媒介**的推进：

```
地中海全景（survey）
  → 意大利区域图（survey）
    → 行省边界示意（schematic：古代行省边界为估计）
      → 现代 Rubicone 河实景照片（标注：「今天被命名为 Rubicone 的河流」）
```

每一次切换都在界面上改变呈现方式（底图 → 示意图 → 照片），让读者知道自己在看的是不同性质的东西。
第三段标注古代边界为估计；第四段的标注措辞固定为**「今天被命名为 Rubicone 的河流」**——
不写"卢比孔河"、不写"渡河处"、也不写"候选河流"（"候选"仍暗示存在一个待选中的正确答案，
而古代河道本身已不可考）。

### 4.3 第 2、5 拍：imperium 的四个维度

不使用「合法 → 越河 → 叛国」的单一状态条。四条并行的轨道，各自有自己的变化时点和确定性等级：

| 维度 | 内容 | 说明 |
|---|---|---|
| 法定军事权限 | imperium 的行使范围与行省边界的关系 | 相对最有依据的一条 |
| 政治对手的定性 | 元老院及其内部各派对此事的定性与时序 | 时序与措辞需逐条核实，不能笼统写成"元老院宣布他是叛国者" |
| 凯撒自己的合法性主张 | 他公开援引的辩护理由 | 主要见于他本人著作，属当事人自述 |
| 实际后果 | 军队是否跟随、城市态度、对手的应对 | 事实层面相对可考，但因果解释有争议 |

界面目标：让读者理解**越过边界为何具有重大法律和政治意义**，同时看到这一行为的合法性解释在当时就有分歧。
视觉可以清楚，但不能用过度简化制造不存在的唯一答案。

**桌面端**：四条轨道横向并列，共用一条时间轴，越河竖线是唯一公共对齐点——
四条轨道在该点的反应各不相同（一前、一同、一无、一后），错位本身即论点。

**移动端**：**不做纵向堆叠，也不使用横向滚动画布。**
改为**共享时间节点的四行事件矩阵**——四行始终同屏，时间轴离散为若干共享节点，
纵向滚动推动**同一个时间游标**依次经过；游标停在某节点时，四行同时给出各自状态，
有的行变化、有的行不变。桌面端"横着看错位"，移动端"竖着走一遍，每一站只有部分行在动"。
论点相同，媒介不同。

### 4.4 分层阅读

- 「哪条河」：卢比孔河古代河道无定论，现代候选河流的争议。
- 「骰子已经掷出」：苏埃托尼乌斯的拉丁文与普鲁塔克的希腊文差异，属赌桌用语而非宿命宣言。
- 「元老院最终劝告」：SCU 的合法性在当时即有争议，这是凯撒公开主张的辩护理由之一。
- 「第十三军团」：兵力估计区间与史料依据，以及古代军队数字为何普遍不可直接采信。

### 4.5 候选实物素材（待检索核实）

凯撒军营铸造的"大象"银币（约前 49–48，为军饷所铸，是这一时刻的同代实物）；
拉文纳与里米尼的遗址与地形；现代候选卢比孔河的实景照片。
全部按 §2.5 记录授权，按 §2.4 处理年代与归属的不确定性。

## 6. 视觉系统：两层令牌

深色展厅**只是罗马首轮实验的视觉方向**，不是全站永久主题。

**全站基础令牌**（所有作品共享，换文明也不变）：排版体系、导航、间距节奏、注释系统、
来源与不确定性标记、交互反馈、焦点与键盘可见性、可访问性规范。

**作品 / 场景主题令牌**（各作品自定）：明暗关系、主色、材质、地图与图表色彩、
图像陈列方式、氛围与节奏。

```css
/* base.css —— 全站基础，语义化，不含具体颜色决策 */
:root { --ha-space-*, --ha-type-*, --ha-radius-*, --ha-focus-*, --ha-motion-* }
/* themes/rome-republic.css —— 作品主题，只覆盖颜色/材质层 */
[data-theme="rome-republic"] { --ha-surface, --ha-ink, --ha-accent, --ha-map-* }
```

罗马首轮默认深色，但**史料抽屉与长阅读区域单独提高对比度**，必要时局部反转为浅色阅读面。
不为氛围牺牲正文可读性。

阵营色不用红/绿：色觉障碍不友好，且红=反派的暗示与 brief 第 6 节相冲。
改用明度 + 色相双通道，图例同时给形状差异。

## 7. 里程碑与审核节点

**不在内容与视觉验证之前定死全站数据结构。** schema 在 M1 立一个够用的版本，M5 验证后再调整。

| 里程碑 | 内容 |
|---|---|
| **M0 内容与视觉分镜** | 卢比孔六拍分镜；每拍核心论断；初步史料；地图尺度与媒介转换方案；静态视觉草图 |
| **M1 可扩展工程骨架** | Astro 工程；公共内容字段；renderer 注册机制；基础设计令牌；一条最小场景可运行 |
| **M2 卢比孔核心垂直切片** | 边界、权限变化、越河表达；接入真实地理数据；接入初步来源与不确定性标记 |
| **M2.5 低保真发现入口** | 跑通地图—时间—作品—场景，尽早验证产品入口 |
| **M3 史料与分层阅读系统** | 论断标记；来源抽屉；人物与争议内容；图像授权；复原内容标记 |
| **M4 完整卢比孔场景** | 六拍内容；桌面与移动端；减少动效；键盘操作与基本可访问性；性能与视觉打磨 |
| **M5 扩展验证** | 再实现一种非地图场景，检验公共结构是否真能支持不同历史表达；验证后再调整 schema |

**审核节点（三次）**：

1. **M0 完成后** —— 审核叙事与静态视觉；
2. **M2.5 完成后** —— 审核核心交互与发现路径；
3. **M4 完成后** —— 审核发布级体验。

### M2.5 低保真入口的验收标准

不要求精美，但必须能实际操作，并跑通：

- 用户可以选择罗马或地中海区域；
- 可以选择"共和国危机，前133—前27年"；
- 可以看到作品及其实验场景，并看到「实验样章」的出版状态标识；
- 可以从入口自然进入卢比孔河场景。

## 8. 首版功能边界（阶段性）

首版不做：账号、收藏、笔记、完整自由探索、完整比较观察、CMS 与后端。
**这是首轮实验的范围边界，不是永久否定**，实验结束后重新评估。

## 9. 已知风险

- **地理数据管道是最长的一环**：AWMC 与 Pleiades 的格式与覆盖需实际拉取验证，
  可能需降级到 Natural Earth + 手工修正古代岸线，届时相应图层的 `accuracy` 必须如实下调。
- **史料核实是内容瓶颈**：按新的来源实体模型，写作速度会明显慢于纯创作，这是刻意的。
- **"不看正文也能懂"** ——M0 静态草图给出了初步答案（四条轨道的变化时点一前、一同、一无、一后，
  错位本身即论点），桌面端成立。但这只是静态构图的成立，**滚动中的动态可读性尚未验证**，
  移动端的四行事件矩阵也还没做出来。M2 核心切片必须实测。
- **renderer registry 可能过度设计**：如果三个渲染器之间共性很少，registry 只是个 switch。
  M5 用第二种非地图场景来检验它是否真的降低了扩展成本。
- **制度授权带尚无视觉方案**：它要同时表达依据哪条法律、期限到何时、是否已过期三件事，
  还要和军团地图共存而不打架。M2 必须回答，M1 建骨架时可以先不解决。
- **拍 1 的人物如何成为可点对象**：人际关系降为按需层后，需要先决定人物在地图上以什么形态存在，
  否则"点选人物展开"没有着落。
